# Infinity Operating System

## Purpose

無限 is a lightweight cross-project memory layer, not a dumping ground.

It should help Codex answer four questions fast:

1. What is the user trying to do?
2. What durable knowledge already exists?
3. Which file should be opened next?
4. What should be promoted, archived, or ignored?

## Core Principles

### 1. Actionability First

Borrowing from PARA, classify knowledge by how it will be used, not only by topic.

- `projects/`: active tools, apps, workflows, bots, dashboards, or ongoing work.
- `libraries/`: stable SOPs, reusable prompt banks, durable frameworks, high-value methods.
- `indexes/`: fast lookup maps, IDs, tags, source paths, and summaries.
- `inbox/`: raw or semi-processed notes waiting to prove they are reusable.

Decision rule:

- If it affects an active build, put it under `projects/`.
- If it is a reusable method, put it under `libraries/`.
- If it is mainly for search and dispatch, put it under `indexes/`.
- If it is new, uncertain, or one-off, put it under `inbox/`.

### 2. Palace Rooms, Not Piles

The memory palace metaphor works best when every memory has a clear location and route.

Use this mental map:

- Front Desk: `README.md`, `catalog.json`, `index.json`
- Search Desk: `tools/search_infinity.py`
- Workshop Wing: `projects/`
- Library Wing: `libraries/`
- Card Catalog: `indexes/`
- Intake Tray: `inbox/`

Every durable note should include enough routing metadata for future recall:

- Type
- Tags
- Use When
- Source
- Project Path, if any
- Next Action, if any
- Related files

### 3. Atomic But Connected

Use a Zettelkasten-like rule: one note should carry one reusable idea or decision.

Avoid giant mixed notes that combine unrelated ideas. Instead:

- One tool idea per card.
- One project decision per card.
- One prompt framework per card.
- One SOP per file.

Each note should still connect outward:

- `Related:` links to project files or other memory cards.
- `Use When:` tells Codex when to open it.
- `Keywords:` include the words the user is likely to say.

### 4. Progressive Summaries

Make every note scannable from top to bottom.

Preferred shape:

1. Title
2. Metadata block
3. One-paragraph summary
4. Key decisions
5. Reuse checklist
6. Details / sources
7. Next action

Do not force future Codex to read a whole long file before knowing whether it matters.

### 5. Retrieval Beats Storage

A note is useful only if it can be found later.

Every new note should include:

- User-facing keywords in Traditional Chinese when relevant.
- Technical keywords in English when tools/models/repos are involved.
- Synonyms for likely user phrasing.
- A precise `Use When` line if promoted to `catalog.json`.

Examples:

- For clothing extraction, include: `服裝分割`, `衣服分離`, `去背`, `SAM`, `SCHP`, `human parsing`, `alpha matting`.
- For crypto scans, include: `Bybit`, `合約`, `回踩`, `TP`, `funding`, `USDT perpetual`.

## Intake Workflow

When the user says `收進無限`, `用無限記住`, or similar:

1. Read `README.md`.
2. Read `catalog.json`.
3. If needed, read this file.
4. Classify the memory type.
5. Write a concise card to `inbox/`.
6. Promote to `libraries/`, `projects/`, or `indexes/` only if it is stable or repeatedly reused.

## Promotion Rules

Promote from `inbox/` when one of these is true:

- The same topic is reused three times.
- It defines an active project or local tool.
- It becomes a standard workflow.
- It prevents repeated mistakes.
- It is a high-value prompt or writing system.

Promotion targets:

- `libraries/`: stable SOPs, frameworks, prompt banks.
- `projects/`: active project memory and durable implementation state.
- `indexes/`: lookup tables and fast search maps.

After promotion, add or update a `catalog.json` entry.

## Catalog Entry Standard

Every catalog entry should be short and dispatch-oriented:

```json
{
  "id": "short-stable-id",
  "type": "methodology | project | prompt_asset | repo_tool | index | tool_idea",
  "path": "relative/path.md",
  "size": "small | medium | large",
  "priority": 80,
  "useWhen": "Open this when...",
  "keywords": ["user phrase", "technical term", "synonym"]
}
```

`catalog.json` is not a note archive. It is a routing table.

## Quality Bar

Good memory:

- Helps a future task start faster.
- Preserves a decision, not just a chat transcript.
- Names concrete files, paths, tools, models, or URLs.
- Includes retrieval keywords.
- Has a clear next action or reuse case.

Bad memory:

- Raw pasted text with no summary.
- One-off facts unlikely to be reused.
- Vague preferences without examples.
- Long notes without a top summary.
- Duplicates of data already indexed elsewhere.

## Maintenance Rhythm

Lightweight maintenance is enough:

- Weekly or after heavy sessions: scan new `inbox/` cards.
- Promote repeated cards.
- Archive obsolete project notes only when they cause confusion.
- Keep `README.md` and `catalog.json` small.
- Do not bulk-load or duplicate images/videos into memory.

## Current Improvement Direction

無限 should evolve toward:

- Better routing through `catalog.json`.
- More reusable knowledge cards in `inbox/`.
- Fewer huge unreadable notes.
- Explicit project state cards for active local tools.
- Search-friendly bilingual keywords.

The goal is not to remember everything. The goal is to make the next useful action easier to find.

# 無限吸收 SOP

Use when the user says `收進無限`, `收入無限`, `放進無限`, `用無限記住`, or asks to save durable reusable knowledge into `D:\codex\memory-palace`.

## Goal

Do not merely archive pasted text. Convert it into reusable knowledge that can later support tools, prompts, writing, websites, novels, skills, or project decisions.

## Required Read

Before writing, read:

1. `D:\codex\memory-palace\README.md`
2. `D:\codex\memory-palace\index.json`

For prompt, image, style, video, portrait, or X-writing material, also consult the relevant existing index/library only when needed.

## Intake Types

Classify each source as one primary type:

- `methodology`: reusable method, framework, SOP, checklist.
- `prompt_asset`: prompt templates, word banks, safe rewrites, negative prompts, camera/style modules.
- `tool_idea`: website tool, local script, workflow automation, product feature.
- `repo_tool`: GitHub repo, app, MCP, API, CLI, installable tool.
- `novel_rule`: fiction-writing rule, chapter structure, continuity constraint, style preference.
- `creative_setting`: character, worldbuilding, scene, visual style, role card, world book.
- `business_growth`: SEO, AdSense, affiliate, X/social content, traffic strategy.
- `project_decision`: durable preference, architecture choice, directory structure, operating rule.

If multiple types apply, choose one primary type and list secondary tags.

## Standard Knowledge Card

Every intake note should use this structure:

```md
# Title

Source:
Date:
Type:
Tags:
Tool Potential: high | medium | low
Prompt Library Impact: yes | no

## 一句話摘要

## 核心內容

## 可重複使用的規則

## 可轉成工具/詞庫的部分

## 對目前專案的用法

## 下次調用關鍵字
```

## Prompt-Related Addendum

If `Prompt Library Impact: yes`, add:

```md
## 詞庫增量

- 可新增標籤：
- 可新增模板：
- 可新增安全替換詞：
- 可新增負面詞：
- 可新增救場詞：
- 可新增範例方向：
```

Do not automatically copy every prompt into `prompt-library`. Mark useful additions first. Only write into the app/library when the user asks or when the current task explicitly includes updating the tool.

## Repo / Tool Addendum

If the source is a repo, app, API, MCP, CLI, or external tool, add:

```md
## 工具判斷

- 能不能本地使用：
- 是否需要帳號/API/付費：
- 是否適合接入目前網站：
- 是否適合做成 Codex skill：
- 風險或限制：
```

Use web verification when the repo/tool may have changed or precise claims are needed.

## File Placement

Default:

- New rough note: `D:\codex\memory-palace\inbox\yyyy-MM-dd-short-title.md`

Promote later only when reused often:

- Stable SOPs: `D:\codex\memory-palace\libraries\`
- Indexes: `D:\codex\memory-palace\indexes\`
- Project-specific notes: `D:\codex\memory-palace\projects\`

Do not copy images/videos into the memory palace by default. Store paths, URLs, tags, and summaries.

## Final Reply

After saving, tell the user:

- saved path
- type
- one-sentence summary
- how it can be used later

Keep the reply concise.

## 一句話摘要

Obsidian 是本地 Markdown 知識庫工具，適合長期沉澱個人素材、方法論、經歷與判斷，再把這些「自己的資料」餵給 AI；對目前工作流來說，它是可選的 UI/筆記層，不必立刻取代無限。

## 核心內容

- Obsidian 是本地優先的 Markdown 筆記軟體，筆記存在本地 `.md` 檔，核心特色是雙向連結 `[[筆記名]]`、關係圖譜與插件生態。
- 個人使用免費；付費主要是官方雲同步與線上發布，新手可以不用。
- 適合筆記體量大、想長期沉澱知識的人；如果只是簡單備忘，普通備忘錄足夠。
- 核心概念：
  - Vault：一個普通資料夾，所有筆記都在裡面。
  - Markdown：純文字格式標記。
  - 雙向連結：A 連 B，B 也能看到 A 引用它。
  - 插件：核心插件與社群插件。
- 新手設定：
  - 預設編輯模式：即時預覽。
  - 新建筆記存放位置：指定收件箱。
  - 附件預設路徑：指定附件資料夾。
  - 核心插件開啟：日記、大綱、書籤、標籤、模板。
- 常用快捷鍵：
  - `Ctrl/Cmd + P`：命令面板。
  - `Ctrl/Cmd + O`：快速切換筆記。
  - `Ctrl/Cmd + N`：新建筆記。
  - `Ctrl/Cmd + E`：編輯/閱讀切換。

## 組織方法

### MOC：內容地圖

建立「目錄筆記」，用連結串起同主題筆記，例如：

```md
# Python 學習地圖
## 基礎
- [[變量與數據類型]]
- [[函數]]
```

適合做主題入口，也可以有 Home 筆記當「地圖的地圖」。

### PARA：用途狀態分類

- Projects：正在推進、有終點的項目。
- Areas：長期負責、沒有終點的領域。
- Resources：興趣與素材庫。
- Archives：已結束、不活躍資料。

### Zettelkasten：卡片盒寫作法

- 一篇筆記只寫一個想法。
- 用自己的話重新表達。
- 主動建立連結。
- 適合寫作、研究與長期素材沉澱。

## 推薦插件節奏

### 第一週

- Calendar：日曆視圖，搭配日記。
- Templater：進階模板，自動日期、標題、提示欄位。
- Image Toolkit：圖片預覽、縮放、拖曳。

### 第二週

- Tasks：跨筆記任務管理與查詢。
- QuickAdd：快速捕捉靈感到指定筆記。
- Periodic Notes：週記、月記、年記。

### 第三週以後

- Kanban：看板流程，例如靈感池 -> 寫作中 -> 已完成 -> 已發布。
- Dataview：把筆記當資料庫查詢，自動生成索引表。
- Excalidraw：白板、思維導圖、流程圖。
- Various Complements：根據現有筆記標題自動補全。

原則：先遇到問題，再裝插件；不要為了看起來強而先裝一堆。

## AI 接入

- 可用 Obsidian Copilot 插件接大模型，實現總結、翻譯、改寫、大綱、基於筆記問答。
- 基本概念：
  - API Key：模型服務鑰匙。
  - Base URL：模型服務地址。
  - Model Name：模型名。
- 文中推薦 DeepSeek 作為低成本方案，流程是取得 API Key -> Copilot 新增 Custom Model -> 設定 Base URL/Model -> 驗證聊天。
- 注意：接 AI 後，筆記內容可能會發給模型服務；私密筆記要注意 API 服務和隱私政策。

## 同步與備份

- 官方 Obsidian Sync：省心、付費、端到端加密。
- iCloud/堅果雲：簡單，但平台依賴與衝突需注意。
- Obsidian Git + 私有 GitHub：同步 + 版本歷史，適合願意折騰的人。
- Syncthing：免費開源點對點同步，配置較麻煩。
- 底線：至少保留一份獨立本地備份。

## 可重複使用的規則

- 先寫再整理，不要先花大量時間設計分類。
- 不追求完美筆記，一行想法也值得記。
- 看到關聯就用 `[[雙向連結]]`。
- 不把 Obsidian 當純收藏夾；收藏時至少寫一句「為什麼值得看」。
- 外部資料導入後要用自己的話重寫，否則只是搬運。
- 插件按需求逐步安裝，避免啟動慢和工作流混亂。

## 可轉成工具/詞庫的部分

- 可做「Obsidian Vault 初始化器」：建立推薦資料夾、模板、收件箱、日記、周記、MOC 首頁。
- 可做「Markdown 模板庫」：日記、讀書筆記、會議、項目計畫、知識卡片、周復盤。
- 可做「無限到 Obsidian 導出器」：把無限 inbox/libraries 轉成 Obsidian 可讀 MOC 和索引筆記。
- 可做「角色卡 Obsidian 瀏覽器」：把 `character-cards` 做成 Obsidian Vault，方便用 `[[角色名]]` 串聯。

## 對目前專案的用法

- 目前不需要立刻安裝 Obsidian，因為已有：
  - 無限：`D:\codex\memory-palace`
  - 提示詞詞庫：`D:\codex\projects\prompt-library`
  - 角色卡冊：`D:\codex\projects\character-cards`
  - Codex 可協助搜尋、整理、寫入。
- Obsidian 適合未來當「人類可視化瀏覽層」：
  - 自己打開 UI 看無限筆記。
  - 自己編輯角色卡、小說設定、X 文章 SOP。
  - 用雙向連結把角色、造型、場景、提示詞、文章題材串起來。
- 不建議現在把所有資料搬進 Obsidian；可以先等資料量更大，或你明確想自己用 UI 翻筆記時再做。

## 工具判斷

- 能不能本地使用：
  - 能。Obsidian 是桌面/手機筆記軟體，Vault 是本地資料夾。
- 是否需要帳號/API/付費：
  - 個人使用免費；官方同步和發布付費；接 AI 需要模型 API Key。
- 是否適合接入目前網站：
  - 不適合直接接網站前端；更適合作為本地知識庫 UI。
- 是否適合做成 Codex skill：
  - 適合做「Obsidian Vault 初始化」「無限導出到 Obsidian」「Markdown 模板生成」skill。
- 風險或限制：
  - 插件多會混亂。
  - 同步配置不當可能衝突或丟資料。
  - 接 AI 可能把筆記內容送到第三方模型。
  - 圖片/視頻大量放入 Vault 會膨脹，建議附件獨立管理。

# AI 內容資料庫目錄分層 SOP

Source: user-provided longform note
Date: 2026-05-21
Tags: AI內容庫, 資料夾架構, prompt管理, 圖片歸檔, 記憶層, 工作流

## 核心觀念

高頻 AI 內容生產時，不要把靈感、成品、圖片、外部參考、方法論、跨對話記憶、發布記錄混在同一層。每個資料夾只回答一個問題，根目錄只放入口與中樞，不放具體內容。

## 七層拆分

1. 底座層
   - 存跨模型可復用的視覺語義、構圖、光影、材質、風格、主體、敘事規則。
   - 不存單次案例，不存某模型短期經驗。
   - 可命名為 `core/`、`NBP/`、`visual-system/`。

2. 成品與發布層
   - 存可直接發布、復盤、再次調用的完整內容。
   - 按用途分區，例如人像、構圖、風格、妝容、技巧、場景、文章、方法論、已發布稿。
   - 不按一時靈感亂放。

3. 模型探索層
   - 某模型專屬經驗獨立分流，例如 `image2探索/`。
   - 每條記錄可包含：原始提示詞、分類判斷、樣張路徑、Eagle ID、視覺機制、適用方向、可復用母版、發布記錄。
   - 可跨模型復用的規則再抽象回底座層。

4. 圖片資源層
   - 圖片集中放在 `image/`，不要和 Markdown 混放。
   - Markdown 記錄圖片路徑與資產 ID；圖片檔名帶主題、英文別名、組別、編號。
   - 目標是圖片即使脫離文章，也能從檔名知道用途。

5. 外部參考層
   - 外部 prompt、文章、案例先原樣放進 `others_prompts/`。
   - 先收藏，再判斷可復用的是視覺語義、寫法結構，還是一次性靈感。
   - 不要一看到好 prompt 就直接混入主庫。

   - 用於跨對話接續，不是資料庫正文。

   - 新對話只按路由讀相關記憶，避免全量載入。

7. 歸檔與工具層
   - `_archive/` 放歷史記錄、舊文件、工作記錄歸檔。
   - `scripts/` 放本地工具腳本，例如圖片上傳、批量改名、Eagle 匯入。

# 跨模型提示詞組織方案：情緒法、結構法與混合法

Source: user-provided longform note
Date: 2026-05-21
Type: prompt_asset

## 一句話摘要

好提示詞不是堆形容詞，而是分清每句話在控制情緒、結構、媒介、版式、約束或敘事，跨模型時用「結構鎖結果，情緒補靈魂」最穩。

## 核心內容

這套方法把提示詞拆成不同職責：

- 情緒法：先說畫面要給人的感覺，例如孤獨、優雅、神秘、懷舊。適合風格探索、氣氛先行、保留模型自由發揮。
- 結構法：直接指定主體、構圖、光線、媒介、版式、約束。適合批量換角色、封面、海報、包裝、角色設定板。
- 混合法：先用結構鎖住畫面，再用一句情緒補氣質。這是實戰默認寫法。
- 結果法：描述最終畫面長什麼樣，適合快速直出。
- 過程法：按拍攝、製作、後期流程寫，適合鎖定攝影、布光、材質、工藝。
- 參考法：用時代、媒介、流派、類型做審美錨點。
- 變量模板法：把角色、風格、場景、光線做成可替換槽位，適合批量生產。
- 約束法：寫不可接受結果，避免跑偏，但不能單獨承擔主畫面生成。
- 敘事法：放入隱含故事，讓畫面有張力。
- 媒介法：先鎖作品載體與質感，例如舊雜誌掃描、紙張纖維、印刷網點。
- 設計系統法：把畫面當成版式系統，指定標題、欄目、簽名、留白與層級。

## 可重複使用的規則

1. 情緒詞不能替代畫面錨點。如果結果發散，補主體、構圖、光線、媒介。
2. 同一段不要堆太多相近情緒詞，例如孤獨、憂傷、破碎、絕望、寂寞同時出現會稀釋方向。
3. 結構項越多，越要刪除低信號描述。
4. 攝影參數必須服務可見結果，不要變成無意義堆詞。
5. 固定模板連續使用時，要主動替換風格底座、光線或媒介，避免同質化。
6. 參考法的錨點要少而準，不要同時塞太多互相打架的年代、流派和媒介。
7. 約束法只負責收口，不能取代主體、構圖、光線與媒介。
8. 跨模型復用時，先保留共享視覺語義，再按目標模型改寫語氣與顆粒度。

## 可轉成工具/詞庫的部分

可做成「Prompt 結構檢查器」或「AI Visual Prompt Generator」的新模式：

- 檢查 prompt 裡是否有：主體、風格/媒介、構圖、光線、材質、情緒、約束。
- 自動判斷目前 prompt 偏向情緒法、結構法、混合法、結果法、過程法、參考法、模板法、約束法、敘事法、媒介法、設計系統法。
- 對過度堆情緒詞的 prompt 提醒補畫面錨點。
- 對太模板化的 prompt 建議補一句情緒或敘事。
- 對封面/海報類 prompt 建議補媒介法與設計系統法。


# 2026-05-12 AI Anti-Sycophancy Decision Prompts

Source:
- User-provided Chinese longform note about AI sycophancy and prompt design, 2026-05-12.

Core insight:
- AI often follows the user's initial framing and wraps it in coherent-sounding reasoning.
- This can create false clarity: a direction feels validated even when key assumptions have not been tested.
- High-risk domains:
  - startup ideas,
  - product positioning,
  - career choices,
  - content topics,
  - investment judgments,
  - long-term projects.

Key principle:
- For important questions, do not ask AI to give a conclusion first.
- Ask it to:
  1. decompose the problem,
  2. list missing information,
  3. generate options,
  4. actively argue against the idea,
  5. identify validation steps,
  6. explain when its recommendation would become invalid.

Most useful sentence:
```text
请不要急着认同我。
```

Reasoning-first prompt template:
```text
这个问题对我比较重要，请不要直接给结论。

第一步，列出影响判断的关键变量。
第二步，指出我现在缺少哪些关键信息。
第三步，给出3个可选方案：保守、中性、激进。
第四步，说明每个方案的适合条件、潜在风险和验证方法。
第五步，给出建议，并说明哪些前提变化后这个建议会失效。
```

Adversarial critique prompt template:
```text
请不要鼓励我。请站在付费用户、竞争对手、严格审稿人三个角度，指出这个想法最大的问题。

每个问题都要给出验证方法。

最后告诉我：哪些问题必须马上验证，哪些可以上线后再看数据。
```

Strong falsification prompt:
```text
请先假设我的判断是错的。

列出最可能推翻它的5个证据。

每个证据说明：去哪里验证，以及验证失败意味着什么。
```

Scenario templates:

Content topic:
```text
判断这个选题是否值得写。

先分析受众需求、传播点、信息增量和同质化风险。

再站在读者角度，指出他们为什么可能不想点开。

最后给出修改建议。
```

Product idea:
```text
判断这个产品想法是否值得做。

先分析需求强度、竞品、付费意愿、获客路径和交付成本。

再站在用户和竞品角度指出最大风险。

最后列出上线前最该验证的3件事。
```

Career choice:
```text
帮我分析是否应该转向这个方向。

先列关键变量，再给保守、中性、激进3个方案，每个说明适合条件和风险。

最后指出最可能让人后悔的原因。
```

Buying a course or tool:
```text
判断我是否适合买这个课程或工具。

先分析目标、当前阶段、替代方案和机会成本。

再指出哪些宣传点可能被高估。

最后给出购买前必须自问的问题清单。
```

Usage note for Codex:
- When the user asks whether an idea is worth doing, avoid immediate affirmation.
- Use the above reasoning + adversarial format by default.
- For product/tool/workflow choices, include:
  - current alternatives,
  - user pain intensity,
  - cost of action,
  - failure modes,
  - minimum validation test.
- For writing topics, include:
  - reader demand,
  - click resistance,
  - information gain,
  - saturation risk,
  - sharper angle.

Common pitfalls and fixes:
- Computer Use is not universal:
  - Some websites detect automation or block access.
  - Use Playwright for structured web admin tasks.

Tags: telegram-bridge, codex-automation, natural-language-routing, memory-palace, novel-notes, safety

## Durable Decision

For the future Telegram-to-Codex bridge, do not require the user to always type slash commands such as `/novel`, `/mugen`, or `/idea`.

The preferred UX is natural-language first:

- "這段小說節奏太慢，幫我記到無限"
- "第 12 章女主反應不合理，收進小說意見"
- "把這個提示詞存進無限"
- "幫我把剛剛那段改成更狠一點"
- "這張圖腳又歪了，記錄成負面提示"

Slash commands can remain as optional backup routes when the message is ambiguous, but they should not be the normal required workflow.

## Routing Rules To Implement

Use intent keywords and conservative routing:

- Messages containing "無限", "收進", "記到", "存起來" should route to memory-palace capture.
- Messages containing "小說", "章", "劇情", "角色", "節奏", "伏筆", "人設" should route to novel reading/comment notes.
- Messages containing "提示詞", "詞庫", "prompt" should route to prompt-library or prompt-memory capture.
- Messages containing "改寫", "重寫", "潤色", "加強", "更狠", "更自然" should route to rewrite/edit actions.
- Messages mentioning image defects such as "腳歪", "手錯", "臉崩", "畸形", "比例錯" should route to image-prompt negative/avoidance notes.

## Safety Boundary

Natural language is allowed for low-risk capture and drafting actions.

High-risk actions still require explicit confirmation, especially:

- deleting files
- bulk editing project data
- executing shell commands
- posting externally
- overwriting prompt-library entries

Unknown or ambiguous Telegram messages should be acknowledged and filed as an inbox note or ask for clarification, rather than executing a risky action.

## Implementation Preference

If building the bridge under `D:\codex\projects\tg-codex-bridge`, implement both:

- natural-language intent routing as the primary path
- slash commands as an escape hatch and testing/debug path

The user wants to be able to write novel feedback in Telegram while reading, and have Codex later receive it, save it, organize it, or execute the requested follow-up.
